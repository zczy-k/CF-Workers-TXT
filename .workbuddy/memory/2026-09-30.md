## 提出优化方案（待用户决策）

用户要求评估「文本云盘」的交互友好度与文本兼容性（尤其 Markdown），给出优化方案。

### 现状盘点（基于 worker.js 3589 行实测）
- 文本判定：`isText()` 靠 159 个扩展名 + `TEXT_APP` MIME 白名单，覆盖已很全
- 查看器：纯 `<pre>`（line 1336），无渲染、无高亮
- 编辑器：纯 `<textarea>`（line 1354），无行号/查找替换/快捷键
- 搜索：`action === 'search'`（line 629）只匹配**路径片段**，不搜正文
- 删除：永久删除，无回收站
- 二进制：一律下载，无图片/PDF/音视频内联预览；CSP `object-src 'none'`（line 995）
- 读上限：在线编辑 2MB（line 662）
- 主题：无暗色模式（`prefers-color-scheme` 出现 0 次）
- 分享页：`<pre class="viewer">` 纯文本
- 目录树排序：`localeCompare(name, 'zh')`，无用户可选排序

### 方案分四档
1. 文本兼容性（建议优先）：Markdown 渲染双模式 + TOC、GBK/GB18030 编码识别、CSV/JSON/SVG/HTML 结构化视图、图片/音视频/PDF 内联预览
2. 编辑体验（投入小）：行号栏、查找替换 Ctrl+F/H、Ctrl+S/Tab/Alt+↑↓ 快捷键、括号配对、md 大纲、草稿自动保存、大文件降级渲染
3. 交互与组织（按需）：全文内容搜索+命中上下文、目录树拖拽移动、面包屑、排序切换、回收站、版本历史、收藏/最近、暗色模式
4. 性能与成本（可延后）：ETag/304、边缘缓存 `caches.default`、大目录分页、断点续传

### 关键约束（已向用户提示）
- CSP 走 nonce 机制，**不能引 CDN** → Markdown 解析器与高亮器必须内联自己写（估 +800~1500 行，当前 158KB，免费版 1MB 尚有余量）
- Markdown 渲染有 XSS 风险（分享页内容来自他人上传）→ 必须全量转义 + 禁原始 HTML
- PDF/HTML/媒体预览需放宽 CSP（`frame-src` / `img-src blob:`），会降低安全边界
- 回收站/版本历史成倍占 R2 存储，需定保留策略

### 范围澄清（用户追问后）
用户问渲染层是否只覆盖 Markdown。答复：**不是只做 md，而是统一的分派机制**，改造点是把 `openFile()`
的单一出口变成「类型判定 → 渲染器分派表」。文本类共 6 个渲染器：Markdown / JSON 树 / CSV 表格 /
代码高亮 / SVG·HTML 预览 / 纯文本兜底。二进制类另走「下载 / 媒体预览」（唯一需要放宽 CSP 的分支）。
渲染器只在**查看**路径生效；编辑仍是源码模式（高亮是叠加增强），保证零回归。
同一套渲染器三处复用：管理端查看、管理端编辑、访客分享页。

### 资源消耗核算（用户追问）
核对了 Cloudflare 当前免费额度：Workers 10 万请求/天、**10ms CPU/次**、脚本 **3MB**、内存 128MB；
R2 10GB 存储、Class A（写/列表）100 万/月、Class B（读）1000 万/月、**出站免费**、
**DeleteObject 属免费操作**；KV 10 万读/天但**仅 1000 写/天**。

结论（当前 worker.js = 155 KB）：
- **第一档 + 第二档 ≈ 零服务端成本**。关键前提：**渲染必须在浏览器端做**，Worker 只吐字节。
  脚本体积 +60KB（155→215KB，占 3MB 上限 7%）。Worker CPU / R2 存储 / R2 操作 / KV **全部为 0**。
- **第三档才有真实消耗**，按严重度排序：
  1. **版本历史** → R2 存储最大增长点（保留 N 份即放大 N 倍）
  2. **回收站** → 存储最坏翻倍（但 DeleteObject 免费，不增操作费）；需 30 天生命周期清理
  3. **全文内容搜索** → 唯一显著增加操作次数：每文件一次 `GetObject`(Class B)，500 文件/次搜索
     对策：建 KV 内容索引（存各文件前 4KB），搜索只读 1 个 KV key，不碰 R2
  4. **收藏/最近访问** → 若写 KV 会撞 **1000 写/天** 硬墙，**必须改 localStorage**
  5. **媒体/PDF 预览** → 出站流量增（但 R2 出站免费），计入 Workers 请求数
- **第四档是降低消耗**：ETag/304 减少 Class B 重复读；`caches.default` 边缘缓存大幅降 R2 读。
  注意：断点续传用 R2 多段上传会**增加** Class A（CreateMultipartUpload/UploadPart 均为 Class A），
  需设大小阈值，小文件不要走多段。

### 全文搜索专项分析（用户追问速度与准确率）
两个方案：
- **方案A 直接扫描 R2**：`list` 取全部 key → 逐个 `GetObject` 读正文 → `indexOf` 匹配。
  消耗高：N 次 Class B + **撞 10ms CPU 限制**（索引前需先解码全部文本）。速度随文件数线性劣化：
  100 个 ≈0.6s / 500 个 ≈3s / 2000 个 ≈12s / 5000 个 ≈30s（受"单请求 6 个并发连接"上限约束，
  即使并发也只能压到几秒级）。规模一上去就不可用。
- **方案B KV 内容索引（推荐）**：上传/保存时把正文（建议前 8KB）写进 KV 的索引 key；
  搜索时只读 1 个 KV key 再本地匹配。**R2 操作为 0**，KV 1 次读。
  速度稳定：100→0.1s / 500→0.1s / 2000→0.15s / 5000→0.2s，**与文件数基本无关**。

准确率的代价（关键权衡）：
- 索引只存前 N KB → 超出部分搜不到。建议前 8KB（覆盖绝大多数笔记/配置/代码文件）
- 兜底：对超出 8KB 的文件标记 `truncated`，结果里提示"该文件较大，仅匹配前 8KB"，
  并给"深搜此文件"按钮（单次 GetObject，约 30ms）→ 最终准确率可达 100%
- 匹配语义：沿用现有 `toLowerCase` + 子串匹配。中文子串匹配对自用盘够用；
  若要精确需 bigram 分词（属过度设计，暂不做）
- **KV 写 1000/天**：索引只在上传/保存/删除/移动时写 → 自用场景不会超

其它可复用结论：R2 强一致；KV 最终一致（同区域基本立即，全局最长 60s），单用户无影响；
在线编辑本就限 2MB（L662），所以索引方案性价比更高。

状态：方案与成本核算已给出，用户确认实施。

### 关键坑（都是本地 `--check` 通过但线上必炸的类型）
1. **模板字符串会先处理转义再输出**，所以字符串字面量也会中招，不只是正则：
   - `'\n'` → 输出真换行 → **单引号字符串里的真换行 = SyntaxError**，整页 JS 死
   - `'\\'` → 输出 `'\'` → **字符串未闭合**，后面的代码被吞
   - 正则里的裸反引号 → **直接终结模板字符串**
   - 修法：一律 `'\\n'`；能不用转义就不用 —— 用 `String.fromCharCode(96/92)` + `charCodeAt` 判断，
     左空白用自写 `ltrim()` 而不是 `/^\s+/`
2. **R2 的 cursor 不透明**：分页必须把 `pageSize` 作为 `limit` 下推给 R2，不能自己在一页里切前 N 条。
   mock 的 `list` 也要真的按 limit 截断并回传 cursor，否则本地怎么写都"对"。
3. **索引搜索的作用域**：访客结果路径要去掉分享目录前缀（否则 `openPath` 拼双层 → 404），
   `idxstat` 也要按 scope 统计，避免泄露总数。
4. **`browser.cjs` 里 `ADMIN + '/api'` 已经含 origin**，再拼 `ORIGIN` 会变成 `http://hosthttp://host/...`。
5. `paintEdSeg()` 在 `openEditor` 里被调用时 `ed.name` 还是**上一个文件** → 分段控件串台。
   改成接受 name 参数，并在载入完成后再调一次。

## ✅ 第三轮 UI 迭代（2026-09-30 傍晚）

用户又给了两张截图，提了 4 点 + 一个开放问题（"还有更好的方法吗"）。全部完成并验证：
静态 + 后端 **120** + 浏览器 **190** + 性能 10 全绿。`worker.js` 266KB → **284KB**（290,664 bytes）。

### 1. 分享设置下方能下滑几千像素的空白（真 bug，量证后修）
根因：`#edMirror`（量行高的隐形镜像层）虽然 `visibility:hidden`，但**仍参与布局**，
且 `height:auto` 会随内容长高。一份 200 行文本 → 镜像层 4449px 高 → 作为 `main`（overflow:auto）
的绝对定位后代，**把可滚动区域撑到 4504px**（视口才 900）。
关键：原 CSS 已经有 `overflow:hidden`，**但不够** —— 盒子会跟着内容长高，压根剪不到。
修法：`#edMirror{position:absolute;inset:0;overflow:hidden;...}`，盒子钉死在编辑器高度；
子元素照常布局，所以 `offsetHeight` 量出来仍是真实高度，行号测量不受影响。
实测：`main.scrollHeight` 4504 → **860（= 视口）**，多余 0px。

### 2. 侧栏可拖拽调宽 + 一键自适应
- `:root{--side-w:256px}`，`aside{width:var(--side-w)}`；拖拽只改这一个变量
- `.sideGrip` 压在侧栏边框上的 5px 细条，悬停露出蓝色竖条；`cursor:col-resize`
- 范围 200~620px，双击 / 「目录」右侧双向箭头按钮 / `←→` 方向键（Shift 加速）/ `Home` 复位
- **自适应算法**：对每行算 `(row.offsetWidth - name.offsetWidth) + name.scrollWidth + 该行左偏移`，
  取最大值。`name` 上有 `overflow:hidden`，所以 `scrollWidth` 就是**未截断的完整文字宽度**。
  实测 210px → 492px，目录树里 10 个文件名全部不再截断。
- 宽度存 localStorage；移动端抽屉模式隐藏手柄

### 3. 列表排序（名称/类型/大小/修改时间）
- 服务端 `listDir` 改为「**先列全目录 → 排序 → 按数字偏移切片**」。
  原因：R2 的 list 不支持排序，且它的 cursor 不透明、只能"接着往下读"，
  没法"从第 N 条开始"，所以分页从 R2 cursor 换成偏移量。
- 文件夹恒排最前并按名称排（没有大小/时间可比）
- 前端：表头可点（再点切升降序）、工具栏下拉 + 方向按钮双向同步、偏好持久化
- 首次点某列用"最有用的方向"：大小/时间降序，名称/类型升序
- 新增「类型」列（文档/代码/配置/数据表/图片/视频/音频/PDF/压缩包/文件夹/无扩展名）

### 4. 框选批量选择
- `#viewList` 上挂 `pointerdown` → 4px 抖动阈值 → 画 `.marq` 选框 → 矩形与行相交即勾选
- `requestAnimationFrame` 限流；拖动中 `body.marq-ing{user-select:none}`；只对 mouse 生效
- `Ctrl/Shift` + 拖 = 加选
- 另加 `Shift + 点击` 勾选框做区间连选（记录 `state.lastPick` 锚点）

### 顺带修掉的遗留 bug
底部批量操作条在切到编辑器视图后仍显示，飘在底部**挡住分享设置** ——
`switchView` 里补一次 `syncSelection()`。

### ⚠️ 本轮最有价值的坑：勾选框的激活发生在 click 派发之前
Shift 连选时我用 `preventDefault()` 取消默认勾选再手动设置 `checked`，结果：
**state.sel 有 5 项，但 DOM 里只有 4 个勾上**，而且**不触发 `change`**。
真实顺序是：浏览器先做 pre-activation → 派发 click → 处理器里设 checked →
事件被取消 → 执行 legacy-canceled-activation **把该元素恢复成点击前的值**，正好抹掉刚设的。
修法：`setTimeout(function(){ paintSel(); syncSelection(); }, 0)` 在事件循环之后再刷一遍。
断言必须**同时比 state 和 DOM**，只比 state 会漏（我第一版就漏了）。

### 新增测试手法

## 续 · 移动端多选（长按进多选模式）

用户问："移动端没办法批量拖选吗？怎么样能一次性多选？**但不是全选**。"

### 现状确认（先查再答）
移动端**完全没有多选入口**：框选被 `if (e.pointerType !== 'mouse') return` 显式禁用（很合理，
触屏拖拽就是滚页面），只剩 15×15px 复选框，手指点不准。所以不是"不好用"，是"没有"。

### 本轮抓到的 3 个真 bug
1. **CSS 层叠顺序**：触屏覆盖 `.mulionly{display:inline-block}` / `.ck{width:21px}` 写在了桌面规则
   **前面** → 被同特异性的桌面值（`display:none` / `15px`）盖掉；但同一块媒体查询里对**其它选择器**
   的规则（`#list tbody tr{touch-action:pan-y}`）却正常生效 → 现象是"媒体查询明明匹配了，
   怎么只有一半生效"，差点误判成"headless 不支持这个媒体查询"。
   修：触屏块整体移到所有桌面规则之后。
2. **长按检测排除了 `<a>`** → 移动端一行里大部分面积就是文件名链接，等于"长按文件名没反应"，
   功能直接失效。修：只排除 `button,input,select,label,option,#list .ops`。
3. **click 抑制窗口太粗暴**：只按"时间窗口 + 落在列表内"判断 → 用户长按后紧接着点「重命名」

   补发 click。**这个 bug 只有把断言写成"点被长按那一行的操作按钮"才抓得到。**

## 续 · 文本框铺满可用高度（编辑器下方不再有大片空白）

用户反馈：编辑器文本框下边缘还有一大段空白，应该自动撑满页面。

### 根因
桌面链条本来是完整的：`body(100vh/列flex) → .layout(flex:1) → main(flex:1/列flex) →
.wrap(flex:1) → #edt(flex:1)`。
**但移动端的媒体查询把它砍断了**：
```css
@media(max-width:900px){
  body{display:block;height:auto;overflow:auto}   /* ← 不再是 flex 容器 */
  .layout{display:block;max-width:none}           /* ← 不再是 flex item，flex:1 失效 */
  main{height:auto;overflow:visible}
}
```
`display:block` 之后下游 `flex:1` 全部失效，高度退化成"由内容决定" —— 打开只有两行的文件时，
整页就只够那两行，文本框下面是空白。移动端尤其明显（`#edt{min-height:46vh}` 只有 46% 屏高）。

### 修法（只改滚动方式，不动 flex 方向）
```css
body{display:flex;flex-direction:column;height:auto;min-height:100vh;overflow:auto}
.layout{display:flex;max-width:none}
main{height:auto;overflow:visible}
.wrap{padding:12px 12px 72px}
#viewEdit{padding-bottom:12px}
```
`min-height:100vh` 负责"至少一屏高"，`overflow:auto` 负责长内容滚动，两者不冲突；
`main` 去掉 `height:100%` 后仍是 flex item，被 `align-items:stretch` 撑满。

桌面端另加 `#viewEdit{padding-bottom:14px}` —— 列表页那 60px 底部呼吸空白对编辑器没用，
只会让人觉得"没铺满"。

### 实测（用只有两行的 `纯文本.txt`，最能暴露空白）
| 尺寸 | 改前 | 改后 | 底部浪费 |
|---|---|---|---|
| PC 1440×900 | — | 767px | 0px |
| 小窗口 1024×620 | — | 451px | 0px |
| 手机 390×844 | **约 350px** | **639px** | 0px |

长文件（300 行）下文本框高度仍是 805px、内容 6656px 在框内滚动 —— 不会被正文顶大。

- 静态 +8、浏览器 **243**（+9）、后端 120、性能 10 —— 全绿
- 新增断言：三种尺寸下 `视口 - 状态栏底边 - padding ≈ 0`、文本框占视口一半以上、
  不满屏时页面不多出滚动条、长内容时框内可滚且高度被视口约束
- 新增探针 `probe4.mjs`（三种尺寸量填充）—— 与 `probe3.mjs`（focus 钩子）一起构成"用量证代替猜"的工具箱
- 新截图 `06-editor-fill.png`（短文件铺满）/ `07-editor-long.png`（长文件内部滚动）/ `m4-editor-crumb.png`

- 两个页面 head 都加 manifest link + theme-color + apple-mobile-web-app-* + apple-touch-icon(180)。

后端验证 PNG 真实性：解析签名/IHDR 尺寸 + `zlib.inflateSync` 解 IDAT（注意 IDAT 在 33 字节偏移处，

## 续 · 修真 bug：文件夹批量上传后全文搜索部分失效（并发丢索引条目）

用户反馈：单文件上传后全文搜索正常；**上传文件夹后部分文件搜不到**。

### 根因（两层）
1. **并发竞态（主因，真 bug）**：uploadTree 用 `pool(jobs, runOne, 4)` **4 路并发**上传，而服务端
   每个 PUT 的 `idxUpsert` 是**读整份索引 → 改 → 写回 KV** 的 read-modify-write。并发交错时
   B 基于旧版本写回会**覆盖掉 A 刚写入的条目**，静默丢失 → 部分文件正文搜不到。
   单文件上传不并发，所以"上传文件能用、上传文件夹失效"。
2. 次要因素（设计内）：正文总量 1MB 上限、单文件 >512KB 不索引、大文件走分片只登记元数据——
   都会让"部分文件"只按文件名匹配，感知上像失效。

### 修法
批量上传（okCount > 1）完成后，前端自动 `api('idxstat')` 探测 hasKv，有 KV 就 `reindexAll()`
分批重建（串行、幂等）→ 把竞态窗口丢的条目补回来。无 KV 静默跳过。
**调试中又抓到一个自己的错**：探测用了 `post({action:'idxstat'})`，但 idxstat 是 GET-only 接口，
POST 返回"未知操作" → 改用 `api('idxstat')`（GET）。
另：search 响应新增 `capFull` 字段，索引容量用满时搜索结果下方明示
"正文索引容量已满，新文件只按文件名搜索（INDEX_TEXT_CAP 可调大）"。

### 测试
浏览器新增：批量上传 3 个文本文件（`new File()` 构造 + uploadTree）→ 断言自动触发 reindex →
`search?q=foxtrot` 正文命中 b.txt 且带片段。后端断言 search 返回 capFull。
回归：静态 / 后端 **177** / 浏览器 **270** / 性能 10 全绿。worker.js 319KB（gzip 99.6KB）。**仍未 git commit**。

### 教训
- **"读-改-写"整个共享数据结构 + 并发请求 = 丢更新**。KV 没有 CAS，跨请求无法根治；
  前端"完成后串行兜底重建"是务实修法。根治要 R2 `onlyIf` 条件写或 Durable Object，暂不做。
- **同一 action 走错 HTTP 方法**（POST vs GET）会得到"未知操作"这种含糊报错——
  探测接口时先确认方法。

## 续 · 全文搜索四项优化（用户批准 1234 全做）

① **索引迁 R2 条件写（根治竞态）**：索引存 `__sys__/idx.json`（故意在 ROOT 外，目录列表/删除扫不到）。
`idxLoad(bucket,kv)` 读索引带 etag；`idxUpdate(bucket,kv,mutate)` 条件写骨架——put 带
`onlyIf:{etag}`，冲突重读重放（mutate 必须可重放：正文提取在外做一次，配额判断在 mutate 内基于当前 idx）。
旧 KV 索引（idx:v1）首次访问自动迁移到 R2 并删除。PUT/DELETE/rename/move/批量操作的索引维护全部
`exec.waitUntil` 后台执行——**上传响应不等索引，速度反而更快**。reindex 每批末尾条件写提交，
冲突返回 409 让前端重跑本批（lastKey 未推进，安全）。**索引不再依赖 KV**——没绑 KV 也能全文搜索。
② **深搜定位页**：deepsearch 返回 `hits:[{n,t}]`（行号+行内容，≤20 条，仅 ≤512KB 文件生成——
超大 split 行数组会吃 CPU 预算）；前端 toast 升级为弹窗列表，点击行 → `pendingGoLine` 记录 →
openEditor 载入完成后 `editorGoLine` 跳行（用户主动点击链路，focus 合理）。
③ **搜索语法**：`ext:md`（后缀）、`path:目录`、`"整词"`，**内嵌在 q 里由服务端 parseSearchQuery 解析**
（前端同名函数只管高亮/判断）。只有过滤词没有关键词 = 列出该类型全部文件。
④ **整词匹配**：`"cat"` 不命中 category；顺带修了 ciFind 老缺陷——原来只试全小写/全大写两种形式
会漏配混合大小写，现在 ≤256KB 统一 toLowerCase，超大文本退回双 indexOf 省 CPU。

### 踩坑记录（重要）
- **改完 worker.js 忘了重新 `cp worker.js t.mjs`** → backend.mjs 跑的是旧代码，4 个 FAIL 全是假的，
  白查半天。**每次改完必须重新拷贝再跑**（t.mjs 是测试的导入副本）。
- MockR2 补了 R2 条件写语义：`onlyIf.etag` 不匹配 → 返回 `{etag: undefined, preconditionFailed: true}`
  不写入不抛错（与真实 R2 一致）；`_wrap` 补了 `etag` 字段（真实 R2 get 返回有 etag）。
- backend 的 mk() 在 call 内 flush waitUntil 队列（`await Promise.all(exec.waits.splice(0))`）——
  mock 的 waitUntil 只是挂起不执行，不 flush 则索引断言全部失效。
- chunk 偏移、KV key 位置之类的**硬编码**在结构变化后必须跟着改（IDAT 偏移、idx:v1 读取点）。

### 回归
静态 ✅ / 后端 **188** / 浏览器 **270** / 性能 10 全绿。worker.js 329KB（gzip 103KB）。
资源影响：搜索 1 次 R2 Class B、每次上传 +1A+1B（对比免费额度百万级无感）；**KV 写配额全部释放**
（索引不再写 KV）。README 搜索章节已重写。**仍未 git commit**。

## 续 · 搜索目录命中成条（方案A）+ 文件打开提速

用户发现搜目录名（如 fniao）时，目录下所有文件都被标成「文件名」命中且文件夹本体缺席。
方案：**目录命中独立成条 + 标注如实细分**。

### 实现
- 服务端 search：命中三分——`nameHit`（basename）/ `pathHit`（目录段带出来的）/ 正文；
  路径命中文件的**祖先目录**收集成集合（内存聚合，无需新数据），与关键词匹配的目录作为独立条目
  返回（`isDir:true, dirHit:true`），排最前；排序 rank = 文件夹3 > 文件名2 > 路径1 > 正文0。
  无索引分支（R2 list 扫描）同样处理。返回新增 `pathHits/dirHits` 统计。
- 前端：标签三分支（文件夹/文件名/路径，CSS .sr-tag.dir 绿、.path 灰）；文件夹条目带
  `data-isdir="1"`，点击委托 → `load(目录)` + 关抽屉；note 统计加"文件夹 X · 路径 N"。
- **文件打开提速（卡顿根因）**：`openPath` 原来是 **list → 等完成 → openFile → read 两次请求串行**，
  中间还夹两次全量重绘。改为 state.path 先行切换、**read 与 list 并行**发出（list 只负责刷新
  列表视图，回来时多半已停在编辑器）——打开延迟减半。另：openEditor 的 read 期间 `#edt` 加
  `.edt-loading` 半透明（可见的"读取中"，消除"点了没反应"错觉），mdOutline 延后一帧
  （大 md 解析不是首屏必需）。

### 回归
静态 ✅ / 后端 **193** / 浏览器 **277** / 性能 10 全绿。新截图 `11-search-dir.png`
（文件夹条目 + 路径标注）。worker.js 334KB（gzip 105KB）。**仍未 git commit**。
（注：shots.mjs 的搜索词要用 serve 播种数据里真实存在的目录名，browser 测试造的目录不在 shots 环境里。）

## 续 · 打开文件"不够丝滑"→ 内存缓存 + 悬停预取

### 实测（probe7）
| 文件 | read 往返 | 赋值 | 行号 | 合计 |
| --- | --- | --- | --- | --- |
| 6KB | 3ms | 0 | 0 | 3ms |
| 65KB | 5ms | 1 | 0 | 7ms |
| 669KB | 19ms | 13 | 1 | 36ms |

**结论：前端渲染不是瓶颈**（669KB 也才 36ms，其中渲染 17ms）。慢的是"每次 openEditor 都发一次
完整网络往返去 R2 取，且零缓存"——真实网络下小文件 150~300ms、大文件 300~800ms。

### 实现（方案1+2）
- `fileCache`：LRU 内存缓存（8MB / 30 条双上限，淘汰时跳过当前正在编辑的文件）；
  条目带 `{text, enc, etag, bytes}`。命中 → **同步立即渲染（0 往返）**，同时 `revalidateFile()` 发
  `If-None-Match` 条件请求：304 静默；变了才更新缓存，且仅在"用户还停在这个文件 && 未改动"时
  热替换编辑器内容并提示。
- 失效钩子：`afterPathChange`（改名/移动，源+目标）、saveEd（缓存换新内容、etag 置空）、
  单个删除、批量删除、批量移动、uploadSimple/uploadMultipart 覆盖上传 → `fileCacheDel/DelPrefix`。
- `renderEdContent()` 从 openEditor 的 then 里抽出来，缓存命中与网络路径共用（含 pendingGoLine 跳行、
  offerDraft）。
- `prefetchFile()`：mouseover 委托（树节点/搜索结果/列表行），停 130ms 才发请求，只预取 ≤256KB、
  最多 2 并发；`hover:none and pointer:coarse` 时跳过（与样式表 #btnUpDir 的判断一致）；
  mouseout 取消待执行计时。

### 踩坑
- **测试间数据污染**：缓存测试原本用 `笔记/说明.md` 做外部改写/saveEd，把它的 Markdown 内容改掉了，
  导致后面的分享页渲染断言（依赖该文件的 md 内容）连带失败 3 项。改用专用文件
  `笔记/cache-测试.md` 并在段尾删除。
- 一次失败的 python 批量替换在 browser.mjs 里留了 `await ev('fetch(BASE + ... )')` 这种
  含字面量 `...` 的垃圾行（模板字符串里看不出来），报 `SyntaxError: Unexpected token '...'` 才暴露。
  **批量替换要打印替换计数并复查**。
- 又忘了 `cp worker.js t.mjs` 就跑测试 → ERR_MODULE_NOT_FOUND。**改完必须重新拷贝**（已记过一次）。

### 回归
静态 ✅ / 后端 **193** / 浏览器 **287**（新增 10 项：缓存命中 0 等待、命中不再发无条件 read、
后台条件校验、外部改动热更新、保存后缓存同步、悬停预取、触屏跳过）/ 性能 10 全绿。
worker.js 342KB（gzip 108KB）。**仍未 git commit**。
